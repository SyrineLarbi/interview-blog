2. Walk me through your most technically complex project.
Say this — HR Insight AI

"HR Insight AI. It predicts employee attrition — who's likely to leave, why, and what retention would cost. I built it because I'd worked on HR systems and everyone had the data and nobody could act on it."

"Architecture. Three services. A NestJS API as the system of record with Postgres and Prisma. A separate Python FastAPI service serving an XGBoost model. And a Next.js dashboard. The reason the model lives in its own service rather than in the Node process is that they have completely different lifecycles — the model gets retrained and redeployed on its own schedule, it has Python dependencies I don't want anywhere near the API, and if inference is slow or down I want the rest of the platform to keep working."

"The hardest part was report generation. It's a six-stage pipeline — fetch, feature-build, inference, aggregate, LLM summary, render — and it takes long enough that a request/response call would time out and the user would stare at a spinner with no idea whether it was working. So I stream live progress to the client over WebSocket, stage by stage. That changes the perceived experience completely, and it also means a failure tells you which stage failed rather than just failing."

"The part I'm most careful about is the RBAC. Four roles — Admin, HR Manager, Team Manager, Viewer — and I enforce it at the query level, not in the controller. A team manager literally cannot construct a query that returns another team's data, because the scope is applied when the query is built. Checking permissions in the controller and then running an unscoped query is how data leaks happen: one forgotten check and the whole thing is exposed. Every mutating action is also audit-logged with actor, entity and IP."

"There's also a what-if simulation mode — HR can model the attrition impact of changing engagement, overtime, pay or promotion cadence — plus per-team analytics, a cross-team heatmap, PDF export, and deep health probes for the database, the ML service and the LLM separately, so I know which dependency is down rather than just that something is."

Expect these:
  • "Why XGBoost and not a neural network?" → "Tabular data with modest row counts — gradient boosting outperforms deep learning on that shape of problem, trains in seconds, and gives me feature importance, which matters because HR needs to know why someone's flagged. An unexplainable attrition score is useless in that context, and possibly unethical."
  • "How do you know the model is any good?" → Be honest: "I evaluate on a held-out set and I care more about recall than raw accuracy, since missing someone who leaves costs more than a false alarm. I'd also say the class imbalance is real and it's the thing I'd want to keep working on."
  • "What would you do differently?" → "Version the model and store which version produced each prediction. Right now a prediction from three months ago isn't reproducible, and for anything affecting people's careers it should be."

2Round 2 — Backend, databases and APIs

6. Tell me about the 50-second query. All of it. They will dig

Know this cold. It's the strongest thing on your CV, so it gets the most scrutiny. Vagueness here reads as "I read about this" and undoes the whole claim.

Say this

"The leave-approval screen in the production HR platform was taking about fifty seconds to load. Managers were effectively blocked from approving leave."

"I reproduced it first, then isolated the cost to the query fetching the approval list — not the rendering, not the network. Then I read the execution plan, and there were three separate problems rather than one."

"One: the join columns had no supporting index, so it was doing full table scans on every load. Two: there were tables joined in whose columns were never actually used in the response — they'd been added at some point and nothing depended on them any more, but every one was still being joined. Three: the SELECT was pulling columns the screen never rendered, so we were moving data nobody looked at."

"I added indexes on the join columns, dropped the unused joins, and narrowed the projection to what the screen actually displays. Fifty seconds to six on the same hardware — about eight times faster. I verified the result set was identical before and after, same rows, before shipping it."

The four follow-ups you will get:
  • "Why is it still six seconds?" — the one they're really waiting for. "Because the remaining time is dominated by result-set size, not by a bad plan. The next steps would be pagination — keyset rather than OFFSET, since OFFSET degrades the deeper you page — caching the approval list, or denormalising the two or three hot fields. I stopped because six seconds unblocked the users and pagination was a product decision I didn't own alone."
  • "What's the downside of adding indexes?" — "They cost write throughput and storage — every insert and update maintains them. You take that trade when reads dominate, which they do on an approval screen that's loaded constantly and written to occasionally. I wouldn't add them the same way to a high-write audit table."
  • "How did you know which index?" — "From the plan: the columns in the join predicates that were driving the sequential scans. Composite where the query filtered and joined on more than one column, with the more selective column first."
  • "Did it change behaviour?" — "No. Same rows, verified against the previous output."
7. How does a database index actually work, and when would you not add one?
Say this

"A B-tree index is a sorted structure that lets the database find rows by a column's value without scanning the table — logarithmic lookup instead of linear. The trade is that it's a second structure the database has to keep in sync, so every insert, update and delete on that column costs more, and it uses storage."

"Where I add them: columns in WHERE clauses, join columns, foreign keys, and anything you frequently ORDER BY. Composite indexes when you filter on multiple columns together — and there the order matters, because a composite index on (a, b) helps a query filtering on a, or on a and b, but generally not one filtering on b alone. That's the leftmost-prefix rule and it's the thing people most often get wrong."

"Where I wouldn't: on a low-cardinality column like a boolean or a status with three values, because the index doesn't narrow much and the planner will often ignore it anyway. On a table that's write-heavy and rarely queried that way. And I wouldn't add indexes speculatively — every index is permanent write cost paid for a read benefit you might not be getting. I'd rather measure with the query plan first."

"One thing I'd add from experience: an index doesn't help if the query can't use it. Wrapping the column in a function — WHERE DATE(created_at) = ... — usually defeats it, because the database can't match the expression to the indexed value. You rewrite it as a range on the raw column instead."

Why this works: the leftmost-prefix rule and the function-defeats-the-index point are both things people learn by being burned, not by reading. They're short and they prove the experience is real.
8. What's the N+1 problem? Have you hit it?
Say this

"It's when you run one query to fetch a list, then one more query per item in that list to fetch a relation — so a hundred rows becomes a hundred and one round trips. It's the classic ORM performance bug, and it's insidious because it's invisible on a dev machine with ten rows and catastrophic in production with ten thousand."

"In Prisma the fix is usually include or select on the relation, so it becomes one query with a join, or a batched second query instead of N. In a resolver-style API you'd use a dataloader to batch the lookups per request."

"I've hit it, and what I'd emphasise is how I found it: it doesn't show up as an error, it shows up as a page that's fine in dev and slow in production. So the habit that actually matters is logging queries per request in development. If a single endpoint fires forty queries, something is looping."

// N+1 — one query for leaves, then one per leave for the employee
const leaves = await prisma.leaveRequest.findMany({ where: { status: 'PENDING' } });
for (const leave of leaves) {
  leave.employee = await prisma.employee.findUnique({ where: { id: leave.employeeId } });
}

// Fixed — the relation is fetched with the list, and only the fields the screen needs
const leaves = await prisma.leaveRequest.findMany({
  where: { status: 'PENDING' },
  select: {
    id: true,
    startDate: true,
    endDate: true,
    employee: { select: { id: true, fullName: true, department: true } },
  },
});
Note the select: pointing out that you fetch only the fields the screen renders ties this answer straight back to your 50s→6s story. Interviewers notice consistency like that.
9. How do you design a REST API? Walk me through your thinking.
Say this

"I start from the resources and the operations the client actually needs, not from the database tables — those are usually similar but not identical, and mapping the API one-to-one onto your schema means every schema change becomes a breaking API change."

"Then the conventions: nouns not verbs, plural collections, nesting only one level deep. GET /leave-requests, GET /leave-requests/:id, POST /leave-requests, PATCH /leave-requests/:id. Correct status codes — 200, 201 with a Location header on create, 204 on delete, 400 for a malformed request, 401 unauthenticated, 403 authenticated but not allowed, 404, 409 for a conflict, 422 for semantically invalid."

"Things I insist on. Validation at the boundary — in NestJS that's DTOs with class-validator and a global validation pipe, so nothing unvalidated reaches a service. Consistent error shape across every endpoint, because clients have to handle errors and inconsistency there is how you get defensive junk in the front end. Pagination on every collection from day one — a collection endpoint with no pagination is a production incident waiting for the data to grow. And versioning, or at least a plan for it, before the first external consumer."

"Two things I'd flag from experience. Non-CRUD actions don't fit neatly — 'approve this leave request' isn't really a PATCH. I'd model it as a sub-resource, POST /leave-requests/:id/approval, rather than bending the verb, because the action has its own rules and its own audit trail."

"And idempotency on anything that mutates money or state. If the client retries after a timeout, the second call must not create a second record. That's an idempotency key on the request, and it's the thing most often left out until it causes a duplicate."

10. How does authentication work in your system? JWT vs sessions?
Say this

"In the HR platform, authentication is Okta SSO — the identity provider handles login and MFA, and my application trusts the token it issues. That's the right call for an internal company-wide tool: I don't want to own password storage or reset flows for a thousand employees, and it means access is revoked centrally the day someone leaves."

"On JWT versus sessions generally — the real trade is revocation. A session is server-side state, so you delete it and the user is out immediately. A JWT is self-contained and stateless, which scales nicely, but you can't un-issue it: if it's valid for an hour, it's valid for an hour even if you've just disabled the account. The usual compromise is short-lived access tokens with a refresh token you can revoke, which gives you most of the scalability and caps the exposure window."

"Storage matters too. Putting a JWT in localStorage means any XSS on your site can read it. An httpOnly cookie can't be read by JavaScript, but then you need CSRF protection. Neither is free — you pick which attack you'd rather defend against, and I'd generally take httpOnly cookies plus SameSite."

"On authorisation, which is the part that actually matters — I enforce RBAC at the query level rather than in the controller. In HR Insight AI there are four roles and the scope is applied when the query is built, so a team manager can't construct a request that returns another team's data. Checking in the controller and then running an unscoped query works right up until someone adds an endpoint and forgets the check."

Why this works: the "authentication is easy, authorisation is where the bugs are" instinct, plus naming the localStorage/cookie trade honestly rather than reciting one as correct, is exactly the security maturity interviewers probe for.
11. When would you use PostgreSQL versus MongoDB?
Say this

"My default is Postgres, and I'd want a specific reason to move off it."

"Relational fits when your data has relationships you'll query across — which is almost always true in business software. Employees, leave requests, approvals, teams: everything is joins. You get transactional integrity, foreign keys that actually prevent orphaned rows, and a query planner that's had thirty years of work put into it. And crucially you can ask questions of the data you didn't anticipate when you designed it, which is exactly what happens with any system that lives more than a year."

"I'd reach for a document store when documents are genuinely self-contained and the shape varies — event payloads, flexible content, third-party responses I don't control the schema of. Or when I genuinely need horizontal write scaling beyond what a single relational primary handles, though that's a much rarer situation than people assume when they choose it."

"I've used MongoDB, and honestly the lesson I took is that schemaless doesn't mean no schema — it means the schema lives in your application code, undocumented, in several versions at once. You end up writing the validation and the migration logic yourself, badly. Postgres also does JSONB well, so you can have a schema for the structured part and flexibility for the part that varies, which covers most of the actual use case."

12. Explain transactions. When have you needed one?
Say this

"A transaction groups operations so they all succeed or all roll back — the database never ends up in a half-applied state. ACID is atomicity, consistency, isolation, durability; the two I actually think about day to day are atomicity and isolation."

"A concrete case from the HR platform: approving a leave request isn't one write. You update the request status, decrement the employee's leave balance, and write an audit record. If the balance update succeeds and the status update fails, you've deducted someone's leave without granting it — which is exactly the kind of bug that's discovered three months later by a very annoyed employee. So those go in a transaction."

"In Prisma that's prisma.$transaction with an interactive callback, so all three writes share the same client and commit or roll back together."

"Isolation is the subtler part. Two managers approving concurrently, or a read-then-write on a balance, can produce a lost update — both read 10, both write 9, and one approval vanishes. The fix is either an atomic operation in the database — decrement rather than read-modify-write — or explicit locking, or optimistic concurrency with a version column. I'd prefer the atomic decrement where the operation allows it, because it's the simplest and it can't be forgotten."

await prisma.$transaction(async (tx) => {
  await tx.leaveRequest.update({
    where: { id: requestId },
    data:  { status: 'APPROVED', approvedById: approverId },
  });

  // atomic decrement — not read-then-write, so concurrent approvals can't lose an update
  await tx.leaveBalance.update({
    where: { employeeId_year: { employeeId, year } },
    data:  { remainingDays: { decrement: days } },
  });

  await tx.auditLog.create({
    data: { actorId: approverId, entity: 'LeaveRequest', entityId: requestId, action: 'APPROVE' },
  });
});
13. When would you add caching? What's hard about it?
Say this

"I'd treat caching as a later resort rather than a first response, because it hides problems rather than fixing them. On the 50-second query, caching would have masked a bad query plan and left the underlying cost in place for the next person. I fixed the query first — that's the right order."

"Where caching genuinely earns its place: expensive computations that are read far more often than they change, data from a slow external service, and anything where slightly stale is acceptable — reference data, aggregate dashboards, config."

"The hard part is always invalidation, and specifically knowing every path that can change the underlying data. Time-based expiry is crude but it's honest — you're explicitly accepting staleness up to the TTL, and it can't be wrong in a way you didn't anticipate. Event-based invalidation is correct when it works and fails silently when someone adds a new write path and forgets to invalidate. I'd lean on TTL for anything where a short staleness window is tolerable, and reserve explicit invalidation for the cases where it isn't."

"I'd also warn about caching per-user data with a key that isn't properly scoped — that's how you serve one user another user's dashboard, and it's a much worse bug than the slowness you were trying to fix."

14. When do you move work to a background job? You mention BullMQ.
Say this

"Anything the user doesn't need to wait for, and anything that can fail independently of the request. Sending emails, generating PDFs, processing uploads, syncing to an external service, scheduled reporting."

"The reasoning is that if I do it inline, three things go wrong: the request is slow, a failure in a secondary concern fails the primary action — the leave request didn't get created because the notification email bounced, which is absurd — and I have no retry story. A queue gives me all three: fast response, isolation, and retry with backoff."

"BullMQ is Redis-backed, so I get persistence, retries with exponential backoff, delayed jobs, and repeatable jobs for scheduled work."

"Two things I'd insist on. Jobs must be idempotent, because at-least-once delivery means a job can run twice — a retry after a timeout where the work actually succeeded. If running it twice sends two emails or creates two records, that's a bug waiting for a bad network day. And you need a dead-letter path plus monitoring: a queue silently accumulating failed jobs is worse than a loud error, because nobody finds out until a user asks where their report went."

Why this works: "the leave request failed because the email bounced" is a concrete absurdity that makes the principle memorable. Idempotency and dead-lettering are the two things juniors miss.
15. WebSockets versus polling — how did you decide?
Say this

"I use WebSockets when the server needs to push without being asked and latency matters. In HR Insight AI, report generation is a six-stage pipeline that takes long enough that a plain request/response would time out, so I stream stage-by-stage progress to the client over a socket. The user sees which stage is running rather than a spinner, and a failure tells them exactly where it broke."

"I wouldn't reach for it by default. Polling is simpler, works through every proxy and load balancer without special handling, and needs no reconnection logic. If an update every thirty seconds is fine, polling is the right answer and WebSockets are over-engineering."

"What people underestimate is the operational cost. Sockets are stateful connections, so a client reconnecting needs to recover state — which means the progress has to live server-side, not only in the socket messages, or a refresh loses everything. And with multiple server instances you need a shared adapter, Redis in Socket.IO's case, or a message published on instance A never reaches a client connected to instance B. That's a bug that doesn't exist in development with one process and appears the moment you scale out."

"For one-directional server-to-client streaming, server-sent events are also worth considering — simpler than WebSockets, works over plain HTTP, and progress updates are exactly that shape. I'd consider SSE if I were rebuilding it."

16. What's your testing strategy? You list Jest, Playwright and Cucumber.
Say this

"Roughly a pyramid, weighted by where the risk actually is rather than by dogma."

"Unit tests with Jest for logic with branches — leave-balance calculation, eligibility rules, anything with edge cases. Fast, and they're where I want the exhaustive cases: negative values, zero, boundaries, dates crossing a year end."

"Integration tests with Supertest against the API, hitting a real test database rather than mocks. These are the ones I trust most, honestly. A heavily mocked unit test verifies that your mocks agree with each other — it won't catch a broken Prisma query or a migration that didn't run."

"End-to-end with Playwright for the critical user journeys only: log in, submit a leave request, approve it. Not every screen. E2E tests are slow and flaky in proportion to how many you have, and a flaky suite is worse than no suite because people start ignoring failures — which is when a real failure gets ignored too."

"Cucumber on top for BDD-style scenarios where the behaviour needs to be readable by non-engineers — HR workflows have rules that come from policy, and having the scenario in language a business owner can check is genuinely useful. I'd be honest that Cucumber adds indirection and I'd only use it where someone non-technical actually reads it. Otherwise it's ceremony."

"On coverage as a target — I don't chase a percentage. It's easy to get 90% coverage that asserts nothing. I'd rather have thorough tests on the leave-balance logic and the permission checks, and nothing on a presentational component."

Why this works: criticising a tool you actually use ("Cucumber adds indirection") signals judgement rather than tool-collecting. The flaky-E2E point and the coverage-target point are both opinions earned from real projects.

3Round 3 — Frontend

17. Next.js: server rendering, static generation or client-side — how do you choose?
Say this

"I choose on two axes: does this content need to be fresh per request, and does it need to be indexed or fast on first paint for someone who isn't logged in."

"Static for content that's the same for everyone and changes rarely — marketing pages, docs. It's a file on a CDN, it's as fast as the web gets, and there's nothing to go down."

"Server-rendered when the content is per-request or personalised and the first paint matters — a dashboard where you want data present in the initial HTML rather than a skeleton that fills in."

"Client-side for anything behind authentication that's highly interactive and where SEO is irrelevant. Most of the HR platform is this: it's an internal tool, everyone's logged in, nobody's Googling a leave request. Server-rendering it would add complexity for no benefit."

"In the App Router the practical version is that components are server components by default and I add 'use client' only where I need state, effects or event handlers — which keeps the client bundle smaller by default. Data fetching sits in server components where it can, and I use TanStack Query on the client for anything that needs caching, background refetch and optimistic updates. That combination is what I'd default to."

"The mistake I'd flag is server-rendering an authenticated dashboard reflexively because SSR is 'better'. You pay in complexity and server cost for a benefit that doesn't apply behind a login."

18. How do you manage state in React? When do you reach for a library?
Say this

"I start by separating server state from client state, because conflating them is the source of most React state complexity."

"Server state — data that lives in a database and that you're caching in the browser. That's TanStack Query's job: caching, deduplication, background refetch, stale-while-revalidate, optimistic updates. Putting server data into Redux means hand-writing all of that yourself, badly, which is what most 'Redux is bloated' complaints are actually about."

"Client state — form inputs, which modal is open, a filter selection. Local useState first, lifted only as far as it needs to go. Context for genuinely global, rarely-changing things like theme or the current user. I'd only reach for a dedicated store if I had complex client state shared across distant parts of the tree, and in three years I haven't needed it."

"For forms specifically I use React Hook Form, because uncontrolled inputs avoid a re-render on every keystroke and it handles validation cleanly — HR forms get large, and a controlled form of forty fields re-rendering on each character is noticeably laggy."

"The general principle I'd state: most state problems are really 'this state is in the wrong place' problems. Adding a library rarely fixes that."

19. A page in your app is slow on the front end. How do you diagnose it?
Say this

"Measure before changing anything — the same discipline as the backend query. I'd open the network tab and the performance profiler and find out which of three things it is: waiting on the network, shipping too much JavaScript, or re-rendering too much."

"Network — is it one slow request or a waterfall of dependent ones? A waterfall usually means components each fetching their own data in sequence, and the fix is to lift the fetch or parallelise. And if the payload is huge, that's often the same over-fetching problem I had on the backend: the API returning fields the screen never renders."

"Bundle — check what's actually being shipped. The usual culprits are a heavy date or chart library imported wholesale, and components that could be lazily loaded. Route-level code splitting and dynamic imports for anything below the fold or behind an interaction."

"Rendering — the profiler shows which components re-render and why. Usually it's a context value or an object/array recreated on every parent render, so everything downstream re-renders. Fixes are memoisation, stable keys, splitting a context that's too broad, and virtualising long lists rather than rendering two thousand rows."

"And I'd measure on a realistic device and connection. Everything is fast on a developer laptop on office wifi — that's how performance problems survive to production."

20. What security issues do you actively think about?
Say this

"Four that I handle deliberately in the code I write."

"Injection. Parameterised queries always — Prisma handles that for me, but the moment I drop to raw SQL I use the parameterised form rather than string interpolation. That's the one place an ORM stops protecting you and it's exactly where people get careless."

"Broken access control, which I'd argue is the most common serious bug in business software. Being logged in isn't authorisation. The specific failure is an endpoint that checks the user is authenticated and then fetches a record by an ID from the URL without checking the record belongs to them. That's why I scope at the query level rather than in the controller — the data access itself can't return what you're not allowed to see."

"XSS. React escapes by default, so the real risk is the escape hatches — dangerouslySetInnerHTML and anything rendering user-supplied HTML or markdown. If I have to render user HTML, it gets sanitised with a maintained library, not a regex."

"Secrets and exposure. Nothing in the repo, everything through environment variables and the secret store. And on the API side, not leaking internals in error responses — a stack trace in a 500 tells an attacker your framework, your file layout and sometimes your query."

"I'd also mention file uploads, since I built the S3 document upload: validate type and size server-side rather than trusting the client, never trust the supplied filename, and serve via time-limited signed URLs rather than making the bucket public."

Why this works: leading with broken access control rather than SQL injection shows you know what actually breaks in modern business applications, and it ties back to the RBAC design you already described. The file-upload detail proves it's from real work.

21. Walk me through your deployment pipeline.
Say this

"Push to a branch, open a pull request. GitHub Actions runs on the PR: lint, type-check, unit and integration tests, and a build. Nothing merges red. Review, then merge to main, which builds a Docker image, tags it, pushes it to the registry, and deploys to Kubernetes."

"On Kubernetes specifically, readiness and liveness probes matter more than people expect — a readiness probe that returns healthy before the app can actually serve traffic means the rollout sends requests to a pod that isn't ready, and you get errors during every deploy. 22. Something is broken in production right now. What do you do?
Say this

"Stop the bleeding first, understand it second. Those are different phases and mixing them up costs users."

"Assess. What's the actual impact — is everything down or is one feature degraded, and for how many people? That decides urgency and who I wake up."

"Mitigate. If a recent deploy correlates with the start, roll back first and diagnose afterwards. Rolling back is almost always faster than fixing forward under pressure, and a rollback is reversible. If it's not a deploy, is there a feature flag I can turn off, or a degraded mode I can put it in?"

"Communicate. Tell people early, even without a cause. 'We're aware, we're on it, next update in thirty minutes' stops the flood of duplicate reports and stops someone else starting a parallel investigation. This is the step engineers skip and it's the one the business notices most."

"Diagnose. What changed — deploy, migration, config, a dependency, or traffic? Logs and metrics around the start time. The question is always 'what's different now versus an hour ago.'"

"Then a blameless post-mortem. What happened, why it wasn't caught, and one concrete preventive action. And the honest test of whether the process worked: did we find out from monitoring or from a user? If a user told us first, then the real action item is the alerting, not the bug."

Why this works: "roll back first, diagnose after" and "did we find out from monitoring or from a user" are both hallmarks of someone who has actually been on call rather than read about incident response.

5Round 5 — System design

Never start coding or naming technologies. Clarify requirements → estimate scale → sketch the components → pick the data model → then discuss bottlenecks and trade-offs. Talk continuously.

23. Design an order-tracking system for an e-commerce marketplace. Your home turf
Step 1 — clarify (never skip this)

"Let me check what we're building. Is this customer-facing tracking, internal operational visibility, or both? Roughly what order volume — thousands a day or millions? Do status updates come from our own warehouse systems, from third-party carriers, or both? And does 'real-time' mean seconds, or is a couple of minutes acceptable? That last one changes the architecture more than anything else."

Assume they say: both audiences, ~100k orders/day, mixed internal and carrier sources, minutes is fine.

Step 2 — scale estimate, out loud

"100,000 orders a day, maybe 6 to 10 status events each — so under a million writes a day, which is roughly a dozen writes a second average, call it ten times that at peak. That's comfortably within a single well-indexed Postgres primary; I don't need anything exotic for the write path."

"Reads are the asymmetric part. Customers check tracking repeatedly — that's easily ten to a hundred times the write volume, and it's heavily skewed toward recent orders. So this is a read-scaling problem with a very cacheable access pattern, and that's what I'd design around."

Step 3 — components

"An ingestion API receiving status events from warehouse systems and carrier webhooks. I'd make it accept and acknowledge quickly, pushing the event onto a queue rather than processing inline — carriers retry aggressively and will hammer you if you're slow, and I don't want a slow database write to cause a carrier to think delivery of the webhook failed."

"A worker consuming that queue: validate, map the carrier's vocabulary to our canonical status set, write the event, update the order's current state. Mapping is a real piece of work here — every carrier has different status names and granularity, and you want that normalised at the boundary rather than leaking into every downstream consumer."

"A read API serving tracking, cached aggressively."

"And a notification path — an event on a status change fanning out to email or push, asynchronously, because a notification failure must never affect the tracking record."

Step 4 — data model, and the key decision

"Two tables. An append-only order_status_events table — order id, status, timestamp, source, raw payload — and an orders table carrying the current denormalised state."

"The important choice is that events are immutable and append-only. I never update an event. That gives me the full history for free, which operations absolutely will need for disputes — 'when did this actually leave the warehouse' is a question I got asked constantly in my supply chain role. And it makes the system idempotent-friendly: a duplicate webhook is detectable on a natural key of order plus status plus timestamp rather than corrupting state."

"The denormalised current status on the order is the deliberate redundancy — it means the common read doesn't have to scan and sort the event history. It's derived data, so I accept it can drift, and I'd be able to rebuild it from the event log if it ever did."

Step 5 — the bottleneck and the trade-offs

"The read path is the bottleneck, and it's very cacheable: cache current status by order ID in Redis with a short TTL, invalidated on status change. Recent orders dominate reads, so hit rates should be high."

"Events arriving out of order is the correctness problem people miss — carriers do send them late and out of sequence. So I'd order by the carrier's event timestamp, not arrival time, and I wouldn't let an older event overwrite a newer status. That's a rule worth stating explicitly because it's a silent data corruption otherwise."

"Duplicates: at-least-once delivery from carriers means the ingestion has to be idempotent. Natural key, or an idempotency key where the carrier provides one."

"On scaling further — the event table grows indefinitely, so partition by month and archive old partitions to cold storage. And if read volume outgrew a single database, read replicas before anything more dramatic, accepting replication lag on a use case where a few seconds of staleness is genuinely fine."

"What I'd deliberately not do at this scale is reach for microservices or event sourcing as a whole architecture. The volume doesn't justify it and it would cost more in operational complexity than it returns."

Why this works: you clarified, you estimated out loud, you identified the read/write asymmetry early and designed for it, you named a subtle correctness bug (out-of-order events) unprompted, and you explicitly declined to over-engineer. The supply chain aside about dispute history is a genuine advantage — use it.
24. Now traffic grows 10×. What breaks first?
Say this

"I'd resist guessing and say what I'd measure — but if I had to predict, in order: the database read path, then the write path, then the queue workers."

"Reads first, because they're already the dominant load. Mitigation in escalating order: make sure the cache hit rate is actually good before adding hardware — a 60% hit rate usually means the TTL or the key design is wrong, and fixing that is free. Then read replicas. Then reconsider what's being queried; often it's one expensive endpoint, not a general capacity problem."

"Writes second. A hundred-plus writes a second at peak is still fine for Postgres, but index maintenance on a fast-growing event table starts to hurt, and this is where I'd re-examine whether every index on that table is earning its cost. Partitioning by month helps, because writes concentrate in the current partition and its indexes stay smaller."

"Workers third — they scale horizontally, which is the easy case, as long as the work is genuinely idempotent and there's no ordering assumption between workers. Since I made events append-only with timestamp-based ordering rather than arrival ordering, that holds."

"The thing I'd want before any of this is visibility: p95 and p99 latency per endpoint, database query time, cache hit rate, queue depth and consumer lag. Scaling without those is guessing, and the usual outcome is paying for capacity that doesn't address the actual bottleneck. I'd rather find the one slow query — which, from experience, is very often what it really is."

The closing line lands because you have a concrete story behind it. "It's very often one slow query" from someone who found a 50-second one is a credible claim, not a platitude.
25. How to handle a live coding exercise.
The protocol — follow it even if you know the answer instantly

1. Restate the problem. "So, given an array of orders, I need to return the top N sellers by return rate. Let me check — should ties be broken deterministically, and what do I do with a seller who has zero shipments?"

2. Give an example by hand. Work one small case out loud. It catches misunderstandings before you've written thirty lines of the wrong thing, and it shows them how you think.

3. State the naive approach, then improve it. "The brute force is nested loops, which is O(n²). I can do it in one pass with a map keyed by seller, which is O(n) time and O(k) space where k is the number of sellers." Saying this before coding is worth more than silently writing the optimal version.

4. Write it, narrating. Talk continuously. "I'm using a Map rather than an object so I don't have to worry about prototype keys..." Silence is the single most common way candidates fail a coding round with correct code.

5. Test it out loud. Walk through your own example. Then edge cases without being prompted: empty input, one element, all identical, nulls. Finding your own bug is a strong positive signal, not a negative one.

6. Say the complexity and what you'd change in production. "This is O(n log n) because of the sort at the end. In production I'd push this into SQL rather than doing it in the application — the database can do the grouping and the ranking far more efficiently, and I wouldn't be loading the whole order table into memory."

If you get completely stuck: say so, out loud, with structure. "I'm stuck on how to handle the tie case efficiently. Let me talk through what I've considered: I could sort and scan, which is O(n log n), or maintain a heap, which is O(n log k). Let me try the simpler one and optimise if there's time." Interviewers hire people who get unstuck visibly. They don't hire silence.
Your advantage here: you can legitimately steer toward SQL and data modeling, which is where your strength is. "I'd do this in the database" is usually the correct production answer, not a dodge — just write the in-memory version first, then say it.

27. Tell me about a disagreement with a colleague over a technical decision. STAR

8Full mock interview — read out loud

Round 2 · Senior Engineer · technical interview
Interviewer

Your CV says you cut a page load from 50 seconds to 6. Walk me through that. I want the actual detail.

You

The leave-approval screen in our HR platform. Managers were effectively blocked — fifty seconds to load an approval list.

I reproduced it first, then isolated the cost to the query fetching the list rather than to rendering or the network. Read the execution plan, and there were three separate problems.

Join columns with no supporting index, so full table scans on every load. Tables joined in whose columns were never used in the response — added at some point, nothing depending on them any more. And a SELECT pulling columns the screen never rendered.

Added the indexes, dropped the unused joins, narrowed the projection. Fifty to six on the same hardware, and I verified the result set was identical before and after.

Interviewer

Six seconds is still terrible. Why didn't you finish the job?

You

Agreed, it's not good. The remaining time is dominated by result-set size rather than by a bad plan — the plan is fine now, we're just moving a lot of rows.

The next steps would be pagination, and specifically keyset rather than OFFSET, because OFFSET gets worse the deeper you page. Or caching the approval list, or denormalising the two or three hot fields.

I stopped because six seconds unblocked the users, and pagination changes how the screen behaves — a manager scanning forty pending requests at once is a different workflow from paging through them. That was a product decision I didn't want to make unilaterally, so I raised it and moved on to the next thing.

Interviewer

Fine. Downside of adding indexes?

You

Write cost and storage — every insert and update has to maintain them. You take that trade when reads dominate, which they do on an approval screen people load constantly and write to occasionally.

I wouldn't apply the same reasoning to a high-write table like an audit log, where I'd be much more conservative about how many indexes I put on it.

Interviewer

Okay. Design question. Order tracking for a marketplace — hundred thousand orders a day, updates from our warehouse and from carriers. Go.

You

Couple of questions first. Is this customer-facing, internal operational visibility, or both? And when you say real-time, do you mean seconds or is a couple of minutes acceptable?

Interviewer

Both audiences. A minute or two is fine.

You

Good, that opens things up considerably.

Scale first. 100k orders a day, six to ten status events each, so under a million writes a day — call it a dozen a second average, ten times that at peak. That's comfortable for a single well-indexed Postgres primary. Reads are the asymmetric part: customers refresh tracking repeatedly, so ten to a hundred times the write volume, heavily skewed toward recent orders. So this is a read-scaling problem with a very cacheable access pattern, and that's what I'd design around.

Components: an ingestion API taking events from warehouse systems and carrier webhooks. I'd acknowledge fast and push onto a queue rather than processing inline — carriers retry aggressively and I don't want a slow write causing a webhook to be considered failed.

A worker consumes the queue, validates, maps each carrier's status vocabulary to our canonical set, and writes. That mapping is real work — every carrier names things differently — and I want it normalised at the boundary rather than leaking downstream.

Data model: an append-only events table, plus the current status denormalised onto the order.

Interviewer

Why append-only? You're storing a lot of rows you'll never read.

You

Three reasons.

It gives me the full history, which operations will need — "when did this actually leave the warehouse" is a dispute question I got asked constantly in my previous life running fulfillment, and if you've been overwriting a status field you can't answer it.

It makes ingestion idempotent-friendly. Carriers deliver at least once, so duplicates are guaranteed. A natural key of order plus status plus timestamp means a duplicate is detectable rather than corrupting state.

And the denormalised current status is derived data, so if it ever drifts I can rebuild it from the log. If the log is the only copy and I overwrite it, I have nothing to recover from.

On storage — I'd partition by month and archive old partitions to cold storage. The rows are small and the recent partition is the only hot one.

Interviewer

What breaks in this design that you haven't mentioned?

You

Out-of-order events. Carriers genuinely send them late and out of sequence, so an "in transit" event can arrive after "delivered".

If I order by arrival time, I'd overwrite a delivered order back to in-transit, and the customer sees their delivered parcel become undelivered. That's a silent data corruption, not an error — nothing throws. So I order by the carrier's event timestamp and I never let an older event overwrite a newer status.

The second one is clock skew between carriers, which makes those timestamps not strictly comparable across sources. I'd keep the source on each event and be careful about ordering events from different systems against each other rather than assuming a global ordering exists.

Interviewer

[writing] Last question. What's the biggest gap in your experience?

You

I've mostly been the main person on my own area, so I've had less code review and less exposure to other engineers' code than someone with the same three years on a bigger team. I've compensated where I can — side projects that push me into unfamiliar territory, reading source rather than tutorials — but self-study doesn't replace someone senior telling you there was a better way.

That's honestly the main reason I'm looking. I'd rather be the one learning than the one everyone asks.
